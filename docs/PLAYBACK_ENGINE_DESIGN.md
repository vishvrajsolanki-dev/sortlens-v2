# SortLens Rebuild — Phase 2 Playback Engine Design

## 1. Executive Summary

Phase 2 implements the deterministic, reversible event replay and multi-lane coordination engine for SortLens. The playback engine bridges the authoritative C99/WebAssembly execution traces produced by the algorithmic core with the interactive visual telemetry layer.

The engine provides:
1. **Bidirectional Event Replay**: Exact forward application and backward reversal for all trace events generated by `sorts.c`.
2. **Bounded-Time Seeking (`FrameStore`)**: Sparse state checkpointing ensuring seeking to any arbitrary step requires at most $K - 1$ event transitions (default $K = 50$) with a sub-millisecond average seek latency.
3. **Decoupled Animation Timing (`PlaybackClock`)**: Time-accumulator scheduler decoupling browser display refresh rates (60–144 Hz) from user-selected simulation speeds (1–1000 events/sec), with tab-suspension catch-up protection.
4. **Single-Lane Deterministic Playback (`TracePlayer`)**: State machine (`idle`, `playing`, `paused`, `completed`) managing playback, stepping, seeking, and UI subscribers.
5. **Multi-Lane Arena Coordination (`RaceCoordinator`)**: Concurrent orchestration across the 5 syllabus algorithms (Bubble, Selection, Insertion, Quick, Merge) with lockstep progression, independent lane completion, and unified race telemetry.

## 2. Event Semantics and Reversal Contract

The C core (`src/core/c/sorts.c`, `src/core/c/trace.c`) records discrete algorithm events into a circular queue. Every event carries a numeric opcode and four 32-bit payload fields: `a`, `b`, `c`, and `d`.

### Event Mapping & Reversal Matrix

| Event Type | Opcode | Payload Semantics | Mutates Array? | Forward Operation | Reversal Operation (`reverseEventBackward`) |
| :--- | :---: | :--- | :---: | :--- | :--- |
| `EV_COMPARE` | 1 | `a` = idx1, `b` = idx2 | No | `comparisons++`<br>active = `[a, b]`<br>highlight = `'compare'` | `comparisons--`<br>active = `[]`<br>highlight = `'none'` |
| `EV_SWAP` | 2 | `a` = idx1, `b` = idx2 | Yes | `swap(arr[a], arr[b])`<br>`writes += 2`<br>active = `[a, b]`<br>highlight = `'swap'` | `swap(arr[a], arr[b])`<br>`writes -= 2`<br>active = `[]`<br>highlight = `'none'` |
| `EV_WRITE` | 3 | `a` = destIdx<br>`b` = newVal<br>`c` = oldVal | Yes | `arr[a] = b`<br>`writes += 1`<br>active = `[a]`<br>highlight = `'write'` | `arr[a] = c`<br>`writes -= 1`<br>active = `[]`<br>highlight = `'none'` |
| `EV_PIVOT` | 4 | `a` = pivotIdx | No | `pivotIndex = a`<br>highlight = `'pivot'` | `pivotIndex = -1`<br>highlight = `'none'` |
| `EV_RANGE` | 5 | `a` = low, `b` = high | No | `range = [a, b]`<br>highlight = `'range'` | `range = [-1, -1]`<br>highlight = `'none'` |
| `EV_PUSH` | 6 | `a` = low, `b` = high | No | `stack.push([a, b])`<br>`stackDepth++`<br>highlight = `'push'` | `stack.pop()`<br>`stackDepth--`<br>highlight = `'none'` |
| `EV_POP` | 7 | `a` = low, `b` = high | No | `stack.pop()`<br>`stackDepth--`<br>highlight = `'pop'` | `stack.push([a, b])`<br>`stackDepth++`<br>highlight = `'none'` |
| `EV_DONE` | 8 | None | No | `isComplete = true`<br>highlight = `'done'` | `isComplete = false`<br>highlight = `'none'` |

### Critical Core Characteristics Leveraged
1. **`EV_WRITE` Preserves Old Value**: Both Insertion Sort (shifting rightwards) and Merge Sort (copying back from temporary buffer) explicitly store the overwritten value in `ev.c` (`trace_record(..., EV_WRITE, dest, new_val, old_val, 0)`). This allows instantaneous, perfect O(1) reversal without saving complete array copies.
2. **`EV_POP` Preserves Popped Range**: Quick Sort records the range being popped in fields `a` and `b`. Reversal re-pushes `[event.a, event.b]` to restore the exact recursion stack.

## 3. Sparse Checkpoint Architecture (`FrameStore`)

Full array snapshots at every event step for 5 algorithms sorting 100 elements would generate over 50,000 arrays in memory. Storing only the initial state and running from step 0 on every seek would introduce $O(N)$ latency on every user slider drag.

`FrameStore` resolves this using **sparse checkpointing**:
- **Checkpoint Interval**: Checkpoints are captured every $K = 50$ steps.
- **Checkpoint Contents**: Checkpoints record array values, operation counters (`comparisons`, `writes`), and recursion stack (`stack`, `stackDepth`).
- **Memory Footprint**: For a 2,000-event execution, exactly $\lfloor 2000 / 50 \rfloor + 1 = 41$ checkpoints are stored (< 50 KB).
- **Bounded Seek Cost**: To seek to step $S$:
  1. Find nearest checkpoint index $C = \lfloor S / K \rfloor \times K \le S$.
  2. Restore checkpoint state in $O(\text{array length})$.
  3. Apply at most $S - C \le K - 1 = 49$ forward event deltas.
  4. Yield immutable `PlaybackFrame`.
- **Directional Delta Caching**: Sequential forward steps (`stepForwardFrom`) and backward steps (`stepBackwardFrom`) apply 1 delta directly to the cached active state, running in $O(1)$ time.

## 4. Decoupled Playback Timing (`PlaybackClock`)

Animation rendering and simulation speed must never lock each other:
- A user may select speeds ranging from **1 event per second** (in-depth lecture inspection) to **1,000 events per second** (instantaneous race).
- Browser display refresh rates vary between 60 Hz, 120 Hz, and 144 Hz.

`PlaybackClock` employs an **accumulated-time delta model**:
1. At each animation frame tick, `delta = now - lastTimestamp` is accumulated.
2. Steps to advance = $\lfloor \text{accumulatedTime} / (1000 / \text{speed}) \rfloor$.
3. When `stepsToAdvance > 0`, the remainder is preserved and `onTick(stepsToAdvance)` is invoked.
4. **Tab Suspension Shield**: If the user switches browser tabs, `delta` can jump by several seconds. To prevent an uncontrolled surge of thousands of steps upon tab return, `delta` is clamped to `maxCatchupMs = 100ms`.
5. **Pluggable ClockScheduler**: All time calls and animation frame requests route through `ClockScheduler` (`now()`, `requestFrame()`, `cancelFrame()`). Vitest suites inject a deterministic `MockScheduler` to test time without sleep or timing flakes.

## 5. Multi-Lane Race Coordination (`RaceCoordinator`)

The SortLens arena hosts 5 concurrent sorting lanes:
1. Bubble Sort
2. Selection Sort
3. Insertion Sort
4. Lomuto Quick Sort
5. Top-down Merge Sort

### Concurrency Rules
- **Global Timeline**: The global timeline length is $M = \max_{\text{lanes}}(\text{lane.totalSteps})$.
- **Lockstep Stepping**: Advancing by 1 step advances every lane whose `currentStep < lane.totalSteps`.
- **Independent Completion**: Fast algorithms finish early and remain parked at their sorted array state with their final telemetry frozen and visible. Slower algorithms continue until they finish.
- **Race Snapshot**:
  ```ts
  interface RaceSnapshot {
    status: PlaybackStatus;
    progress: number; // currentStep / maxSteps (0.0 to 1.0)
    currentStep: number;
    maxSteps: number;
    isAllDone: boolean;
    lanes: ReadonlyArray<{
      algo: AlgorithmId;
      frame: PlaybackFrame;
      isDone: boolean;
    }>;
  }
  ```
- **Unified Navigation**: Calling `seekProgress(0.5)`, `stepBackward()`, `play()`, or `restart()` updates all 5 lanes synchronously.
